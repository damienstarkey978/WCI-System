   **The clipboard-relay architecture described in earlier versions of this doc is abandoned.** In this session's browser automation environment, every tab reports `document.visibilityState === "hidden"` permanently (even the tab just clicked into), which blocks both `document.execCommand('copy')` (returns `false`) and the async Clipboard API (hangs indefinitely). This is an environment limitation, not fixable from inside the session, so the clipboard/`batch-import` API path was dropped entirely in favor of a new pipeline that needs no cross-origin transfer at all:

   1. In Buildertrend, open the folder (Photos, Documents, or a sub-folder like Daily Logs) and use its native **"Download ZIP of folder"** feature (select the folder or its files → download icon → `POST /api/MediaFolders/DownloadZipOfFolder` for a top-level folder, or `POST /api/Media/DownloadZipOfAttachedDocs` when selecting individual files/a sub-folder like Daily Logs). This lands a real ZIP in the Mac's Downloads folder — for a large folder (e.g. 243 files / 269MB) this can take 40+ seconds; poll `ls -lat` on Downloads and watch the network request's status go from `pending` to `200` to confirm real completion rather than trusting the page spinner alone.
   2. On the user's Mac (via the device bridge), unzip locally into a working folder — **use `~/Documents/wci-migration/<job>/<FolderName>/`, never `~/Downloads`**. Files under `~/Downloads` in this environment report as hardlinked (`nlink > 1`) to `device_stage_files`'s own check even when freshly created, which makes staging fail unconditionally; `~/Documents` (a separately-granted connected folder) does not have this problem.
      - **Filename collisions:** when a folder has duplicate filenames (e.g. many `unknown.jpg`), Buildertrend's ZIP export prefixes each entry with an incrementing index (`0_unknown.jpg`, `54_unknown.jpg`, `0_IMG_1650.jpeg`, `1_IMG_1650.jpeg`, ...). Keep these prefixed names as-is when uploading to WCI — its `File` table doesn't enforce filename uniqueness, and stripping the prefix would silently cause name collisions/confusion, not data loss.
   3. Stage the needed files into the cloud session with `device_stage_files` (batches ≤10MB total, since `file_upload` shares that cap — in practice, stage/upload **one file at a time**, see below). **`file_upload` (Claude in Chrome, driving the user's real Chrome) will only accept a path already staged into *this cloud session's own* `/mnt/user-data/uploads/...` tree — it rejects the file's real path on the user's Mac (e.g. `/Users/damienstarkey/Documents/...`) even though that folder is bridge-connected, with "only files this session is allowed to read can be uploaded." So the correct two-hop path per file is: `device_stage_files` (Mac path → lands at `/mnt/user-data/uploads/Documents/<relative path>` in the cloud session) → `file_upload` using that `/mnt/user-data/uploads/...` path, not the Mac path and not the `~/mnt/Documents/...` device-bash path.**
   4. On the target job's Files page in WCI OS (`/jobs/<jobId>/files`), set the Category select via JS if needed (`document.querySelector('select[name="category"]')`, dispatch a `change` event — clicking the native dropdown is flaky), attach the staged file(s) to the page's own pre-existing "Drag and drop files" input via `file_upload` (do **not** click the file input directly — it opens a native OS picker the automation can't see), then submit via `document.querySelector('button[type="submit"]').click()` (more reliable than clicking a `find`-derived ref, which goes stale quickly). **Don't forget the submit click** — `file_upload` only attaches the file to the input, it doesn't submit the form; a run in this session lost several minutes because the click step was skipped and the page just sat with the file attached.

   This uses only pre-existing, unmodified features on both sides — no backend changes, no new auth bypass.
